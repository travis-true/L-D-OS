# GitHub implementation

The generic v0.2.0 repository includes a dependency-free GitHub Pages intake site, automated validation, and a Pages deployment workflow. Repository owners should complete the [GitHub administration checklist](github-admin-setup.md) after the first validated push.

## Minimum setup

1. Create a repository from this package.
2. Protect the default branch.
3. Require pull requests and the validation workflow.
4. Activate CODEOWNERS by copying `.github/CODEOWNERS.example` to `.github/CODEOWNERS` and replacing role placeholders.
5. Allow the intake-triage workflow to create and maintain its controlled labels from `data/github-labels.json`.
6. Create a project board using the state model in `docs/architecture.md`.
7. Store only permitted records and evidence references in GitHub.

## Governed intake automation

`.github/workflows/intake-triage.yml` runs when an intake Issue is opened, edited, reopened, labeled, or unlabeled. The first merge of the workflow also bootstraps the label catalog and processes existing open Issues whose titles begin with `[Intake]`.

The workflow:

- creates or updates the controlled labels in `data/github-labels.json`;
- parses the structured Markdown generated by the public intake;
- applies the request type, provisional lane, initial risk, state, and information-needed labels;
- detects deterministic gaps, conflicting source-authority language, and non-ISO need-by dates;
- creates or updates one marked triage-preparation comment instead of adding duplicate comments;
- optionally assigns the username stored in the repository variable `LDOS_INTAKE_OWNER`;
- rejects gate labels added by actors who do not have write, maintain, or administrator permission; and
- advances state only when the complete preceding human-gate sequence is present.

State transitions are deliberately limited:

| Required human labels | Automated state |
| --- | --- |
| None or incomplete G00/G02 | `state:triage` |
| `gate:g00-authorized` and `gate:g02-authorized` | `state:diagnosis` |
| Prior labels plus `gate:g01-approved` and `gate:g03-approved` | `state:design` |
| Prior labels plus `gate:g04-approved` and `gate:g05-authorized` | `state:build` |

Labels are workflow triggers and visible routing controls; they do not replace the evidence and authority fields required by `schemas/gate-decision.schema.json`. The workflow never approves a gate, creates learning assets, accepts risk, or releases content.

Use **Actions → Prepare intake triage → Run workflow** with an optional Issue number to reprocess a specific intake. Editing an intake Issue also reruns preparation automatically.

## Pull-request rules

- Link the project or request ID.
- Identify the lane and gates affected.
- Include source, evidence, and candidate references.
- Separate QA disposition from authorization.
- Prevent unresolved blocker or critical findings from merging.
- Require approval by the configured content, accessibility, and release owners when applicable.

## Security controls

- Use least-privilege workflow permissions.
- Do not place secrets, access tokens, credentials, personal data, or restricted source content in issues or repository files.
- Use protected environments for publishing jobs.
- Do not execute code from untrusted pull requests with privileged secrets.
- Pin external actions to reviewed versions or commit identifiers under the organization’s supply-chain policy.
- Preserve build artifacts and provenance for controlled releases.

## Browser-only operation

The process can be run through GitHub’s web interface: issue forms for intake, web-created branches for record changes, pull requests for review, Actions for validation, and Releases for approved packages. Local Git tooling is optional.
